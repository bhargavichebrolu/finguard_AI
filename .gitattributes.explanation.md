# .gitattributes

Source: [.gitattributes](.gitattributes)

## A. File Purpose
Tells Git how to treat line endings for files where the exact bytes matter.

## B. Why This File Exists
The development computer has `core.autocrlf=true`, which can change line endings on checkout. Two kinds of file cannot tolerate that:
- The frozen JSON metadata is checked by SHA-256 when the API starts, so changed line endings would make a good file look tampered with.
- Files under `docker/` run inside Linux containers, where a carriage return can break a script.

## C. Dependencies
- **Libraries / tools:** Git.
- **Internal files:** `artifacts/metadata/*.json`, `docker/**`.
- **External services / database:** none.
- **Depended on by:** every clone of the repository.

## D. Every Function Explained
No functions. The rules:

### `artifacts/metadata/*.json -text`
Git treats these as exact bytes and never converts them.

### `docker/** text eol=lf` and `*.sh text eol=lf`
Git always checks these out with LF endings, on every operating system.

## E. Classes Explained
None.

## F. Execution Flow
Git applies the rules on commit and checkout.

## G. Input and Output
Input: none. Output: consistent bytes in the working tree.

## H. Important Technical Concepts
- **Why not `eol=lf` for the metadata?** `-text` is the stronger promise: Git never touches the content, whichever settings apply.
- **This file does not change frozen results.** Those JSON files already use LF, and their hashes were confirmed before this file was added.

## I. Example
```powershell
git check-attr -a artifacts/metadata/model_v1.json
```

## J. Maintenance Notes
Add any new file whose hash is verified at start-up to the first rule.
