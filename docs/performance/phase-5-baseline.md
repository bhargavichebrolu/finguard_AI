# Phase 5 performance baseline (M2)

Every figure here comes from a saved run file in this folder, produced by `scripts/measure_performance.py` or `npm run perf:pages`. Nothing is estimated. The tables at the end are generated from `phase-5-baseline.json` and `phase-5-pages.json`; regenerate them with `python scripts/measure_performance.py render docs/performance/phase-5-baseline.json --pages docs/performance/phase-5-pages.json`.

**Scope and conditions.** One API process (the default before M3) in Docker Desktop on the host described in the tables, against the browser-test database. Synthetic inputs only; no PaySim data or test partition. These are figures for this machine, not for any hosting platform.

## Findings

1. **Predictions do not scale with concurrency in one process.** Sequential requests ran at about 24.0 per second (p50 37.61 ms); 8 concurrent clients reached only 26.6 per second while p50 rose to 297.93 ms. M3 examines more processes.
2. **Latency varies between sessions.** The same sequential measurement gave p50 24.4–24.7 ms in a smoke run on 2026-11-08 and 37.61–38.72 ms in this run. Comparisons must therefore be paired within one session (see the budget below), never against these stored numbers.
3. **Batches** processed about 1,041.8 rows per second at 50,000 rows.
4. **The dashboard summary was the slowest page request**: p50 862.19 ms at 500,000 predictions, making the dashboard take 1505 ms to be ready while every other page was ready in under 500 ms. Four of its queries each took about 150 ms (EXPLAIN ANALYZE) as separate full passes over the same join.
5. **The predictions CSV export took 109 seconds** for 500,000 rows (98,869,998 bytes), and the API's memory reached 495.6MiB. The export yielded one line per piece, each handed over from a worker thread, and the driver fetched every row before streaming began.
6. **Deep offsets are slow**: the explorer's last page at 500,000 rows took p50 2664.13 ms because of `OFFSET`. The interface's pager moves one page at a time, so a person cannot reasonably reach it; API clients can. Recorded as a limitation; keyset pagination would fix it.

## Latency budget for M3 (set before any M3 code)

M3 may add PostgreSQL-backed rate limiting to the prediction path only if, in a paired comparison, it stays within this budget:

- **Method:** in one session, alternate the memory-based (A) and PostgreSQL-based (B) limiter four times (A, B, A, B), each run being `measure_performance.py latency` (two rounds each of 400 sequential and 1,600 concurrent requests). For each mode and each statistic, take the median across the runs and rounds of that condition.
- **Budget:** B minus A must be at most **10 % of A for p50** and at most **15 % of A for p95**, separately for sequential and for 8-concurrent requests, with a floor of 2 ms where 10 % would be smaller. p95 gets more room because, within this run, sequential p95 varied from 44.95 to 56.4 ms between rounds.
- **Decision:** if any of the four comparisons exceeds the budget, the PostgreSQL limiter is rejected for predictions, as the approval requires; the alternatives in the plan (D2) then apply.
